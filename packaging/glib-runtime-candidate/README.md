## Explicit exclusions and honest result

The chosen GLib flags omit generated API/manual documentation, upstream test builds/installations, generated GIR/typelib binding metadata and optional DTrace/SystemTap/sysprof instrumentation. Typelibs can be runtime dependencies of introspection-based bindings; tracing is an optional runtime capability, not merely documentation. Those capabilities are outside this lane's tested boundary. The GIRepository runtime library itself still builds and is exercised. `BOUNDARY-REVIEW.md` independently checks the exact Pango 1.58.2 and accepted WeasyPrint 70.0 CFFI path and explains why these exclusions do not remove its native C calls.

This is an ephemeral prerequisite subset, not a full GLib release installation: other installed CLI/development tools and install-time hooks are not promoted. Pango needs `glib-mkenums` even with GIR disabled, so it is retained, bound through the upstream `glib-2.0.pc` tool path, and actually run against a first-party enum fixture. A tiny first-party shell adapter invokes the untouched configured script with the pinned Python `-I -S`. No host Python fallback is accepted. Meson 1.11's native-file Python entry truncates argument lists; the candidate deliberately omits that entry and uses the accepted Meson adapter's shared isolated `python_command` default instead.

One additional release generator is executable with an `env python3` shebang: `gen-visibility-macros.py`. Meson would run it directly and bypass that default. The ordinary program override binds this exact source script to the pinned interpreter plus `-I -S`; expanded Ninja commands are inspected before the build and reject direct shebang/non-isolated/host-Python generator calls. The other selected Python generators already use GLib's explicit Python object. The enum fixture uses the source-defined `--eprod=@EnumName@` template field.

A future successful result would establish bounded native behavior for GLib regex/Unicode/main-context dispatch, GObject generic signal marshalling through the selected libffi, libffi executable closures, private GModule loading, GIO local file create/read/delete, GIRepository construction, all 102 msgfmt-built catalogs and a real GLib French month lookup. Mach-O identity and loaded-image checks reject external providers. Success still leaves Pango, rendering, font/data closure, relocation, full installation, release, models and providers false.

For the production-catalog probe, an invalid regex must return GLib's exact unmatched-parenthesis error, exercising GLib's own compiled-prefix gettext initialization. A contextual `g_dpgettext2` lookup then requires `January` to translate to `janvier`. There is no manual domain rebinding. Darwin date formatting legitimately prefers `nl_langinfo`, so it is not substituted for this catalog test.

The proposed single job uses literal standard `macos-26`, no matrix/fallback, only the exact new branch, `contents: read`, pinned checkout without persisted credentials and a public-repository job-level guard. Current official GitHub runner/billing sources in `BOUNDARY-REVIEW.md` establish that the standard public-repository runner has no runner-minute charge; the sole publisher must recheck public visibility immediately before activation. The existing foundation's successful logs measured roughly 32 seconds for pkgconf configure/build, 26 for PCRE2 and 61 for standalone intl, plus containment/integrity overhead. Combining the larger gettext-tools and GLib graph within the old 12-minute limit is not established. The new proposed limit is 30 minutes: 180 seconds for input retrieval, a shared absolute 1,500-second execution deadline and 120 seconds reserved for startup/cleanup. Standard-runner RAM/CPU are unchanged. A timeout/failure is terminal and does not authorize rerun/graph expansion.
